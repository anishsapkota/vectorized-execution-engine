Key property: columnar, not row-oriented All device_id values of a segment live together in one contiguous code array (frame-of-reference encoded, see below). All ts values in another. A query that only reads ts and value never touches device_id memory — even if it's in the same segment.

The toy table above uses 4-row segments so every value fits on screen. The benchmarks load readings into 65,536-row segments (load_csv(readings, csv, 65536)), so 10M rows make 153 segments.

Int64Vector — frame-of-reference encoding

Encoding, per segment column

The constructor takes the column's min as base_ and stores value − base in the narrowest unsigned width that holds the range (max − min):

range ≤codes_ alternativebytes/value
255vector<uint8_t>1
65,535vector<uint16_t>2
2³² − 1vector<uint32_t>4
otherwisevector<uint64_t>8

Each segment picks its own width, so one table column can mix widths across segments.

Reading: visit(), not data()

There is no int64_t* to borrow any more. Kernels call visit(f), which resolves the width once and hands f a typed std::span<const uintN_t> plus the base. The inner loop is a plain widen-and-add:

col.visit([&](auto codes, int64_t base) {
    for (...)  v = Int64Vector::decode(base, codes[i]);
});

value(i) exists for cold paths; raw() returns {codes, base, width} for the compiled engine.

Float64Vector — double or float

values_ is a variant<vector<double>, vector<float>>. A schema column with narrow_float = true is stored as float (4 B). That is lossy in general and exact only for inputs with at most 6 significant digits. Reads always widen to double; visit() hands kernels either span.

Immutability after seal() Columns are built once, at SegmentBuilder::seal(), and have no append API. Until then the builder buffers raw int64_t / double / string values; seal() sorts them (if there is a sort key), builds the sparse index from the raw keys, then encodes each buffer into its immutable Vector. The builder is exhausted and the Segment is const-only, so concurrent reads need no locking. For a narrow-float column, seal() rebuilds the zone map from the stored floats: rounding can move a value past the double min/max, and pruning must agree with what the filter will read.

Primary Index (Sparse)

When a Table is sorted by a key column, each Segment gets a sparse index mapping granule start positions to their key values. Enables binary-search within a segment.

Without index

Scan starts at row 0 and applies the filter predicate to every row. With 65,536-row segments, that's 65,536 comparisons per segment even if only 100 rows match.

With sparse index (granule_size = 8192)

The index has 8 entries for a 65,536-row segment. Binary search finds the first granule that could satisfy ts > cutoff, and the scan starts there — skipping up to 57,000 rows without reading them.

Query ts > 1130: scan_start_row() runs upper_bound over the index for the first granule whose start key is greater than 1130 (granule 2, key 1250), then backs up one granule, because rows of the previous granule can still exceed 1130. Scan begins at row 4 (granule 1) and skips rows 0–3 entirely.

The skip is conservative and granule-sized: for ts > 1100 the same search lands on granule 0 (its start key 1010 ≤ 1100), so the scan starts at row 0 even though rows 0–3 cannot match; the filter discards them. Lt, Le and Ne always start at row 0. The index is only built for a table's sort key, and is used only when the scan predicate is on that column. scan_start_row() is shared by ScanOperator and the compiled engine's host, so both engines read identical row ranges.

The cost — 4 dispatches per row

Inside matches() — per row

  1. std::visit on predicate variant → type dispatch
  2. Generic lambda instantiation
  3. static_cast to typed vector
  4. switch(op) for comparison

All 4 steps are constant for the entire batch — the predicate never changes between rows. Yet we paid for them 10M times.

Why the row model was kept at all ScanRow is conceptually clean for explaining execution — "give me the next row". The Volcano model is in every textbook. We built it first to prove the pipeline works, then replaced the return type with Batch to amortise call overhead. The operator interface (next(), nullopt = done) stayed identical. ScanRow itself no longer exists in src/; this section is history. The vectorized engine (v2) is what main.cpp and wb_bench run, and the compiled engine (v3) runs the same plans next to it.

The filter kernel — branchless, into a reused buffer

// filter.cpp — select_rows(), no-sel case (the sel case loops over batch.sel())
if (out.size() < batch.size()) out.resize(batch.size());
std::uint32_t* dst = out.data();
std::size_t    n   = 0;
for (std::uint32_t i = offset; i < end; ++i) {
    dst[n] = i;        // always store
    n += pred(i);      // advance only on match
}

FilterOperator dispatches once per batch on column type × FOR width (via visit()) × CompareOp. The row loop has no branch on the predicate, so a 50%-selective filter pays no mispredictions.

survivors_buf_ grows to the largest batch and stays there; the emitted batch's sel_ borrows it. A batch with no survivors is skipped, and the filter pulls the next one.

Zero-copy, zero-allocation design The column data is never copied. columns_ borrows ScanOperator::batch_cols_, which is rebuilt once per segment, not per batch. sel_ borrows FilterOperator::survivors_buf_. Building a batch therefore allocates nothing. The price is a lifetime rule: a batch is valid only until the next next() on the operator that produced it (or anything upstream), so operators must not keep batches across calls.

Each pass resolves the column's encoding once (visit()) and is templated on the batch's live rows, a contiguous range or the selection vector, so no row-id array is materialized. MEDIAN — block chains, select at the end

MedianStore<T> keeps values in the column's storage type (int64, double, or float for a narrow column). Each group owns a chain of 2 KiB blocks (256 int64/double or 512 float), carved from 64-block, 128 KiB chunks that never move: no doubling, no copy on growth. Block next/size headers live in side arrays.

At output, grouped MEDIAN copies each chain into a reused scratch array and runs std::nth_element under median_less (−0.0 before +0.0, NaNs last by bit pattern). A global MEDIAN selects in place over its consecutive blocks with an introselect that falls back to heapsort, so the worst case is O(n log n).

What inline state and block chains bought From docs/superpowers/specs/2026-10-21-footprint-fixes-design.md §7 (10M rows, Apple M3 Pro): Q7 MEDIAN-by-group peak memory fell from 382.9 to 89.0 MiB in the vectorized engine. Inline state did not speed up this operator's grouped SUM/COUNT (Q4 vec 26.8 → 28.8 ms): per-aggregate passes read better from a dense state array than from state spread over a slot table. It did help the compiled engine's fused loop (Q4 25.4 → 12.4 ms).

A separate, older path: parallel_group_sum_count() (src/exec/parallel_agg.cpp) does SUM/COUNT only, straight over segments, into flat AggHashTables (key → {sum, count}, pre-sized to 32,768 slots). It does not use HashAggOperator or GroupSlots.

HashJoin — Sorted Build, Reused Output

HashJoinOperator (src/exec/hash_join.*): inner equi-join on one int64 key. The build side blocks on the first next(); the probe side streams. Output columns are every probe column, then every build column; duplicate keys on either side produce the full cross product per key.

A probe row with key 7 finds one bucket and emits build rows 2 and 3 — they are contiguous because the build chunk is sorted. stable_sort keeps equal keys in their arrival order. Bucket positions come from the top bits of the multiplicative hash, since its low bits depend only on the key's low bits.

Output never spans two probe batches

Pulling the next probe batch invalidates the current one, so next() emits what it has before calling load_probe_batch_() again. A key with more matches than fit is continued on the next call (match_pos_).

Reused output columns

For Int64/Float64 joins the operator owns one output Vector per column and refills it in place every call: Int64Vector::reset_plain(n) (width 8, base 0) and Float64Vector::reset(n) keep capacity, so steady-state batches allocate nothing. A join with a String column falls back to sealing a fresh chunk per batch.

Effect From 2026-10-21-footprint-fixes-design.md §7: reusing output columns took Q5 (join + group by region, 2M orders × 100k customers) from 21.8 to 11.5 ms in the vectorized engine, and allocations per run from ~31,000 to 301. The per-batch output allocations are gone; what remains is fixed per-query setup.

v3 — Compiled Pipelines

A HyPer-style second engine. The same logical plan is turned into C++ with one fused loop per pipeline, compiled with clang into a shared library, loaded with dlopen and cached. Results match the vectorized engine bit for bit.

Plan IR

Scan, Filter (AND of compares), HashJoin on int64 keys, and an Aggregate allowed only at the root. Column references are positions in the child's output. validate_query() type-checks the tree before either engine sees it.

Compiler and cache

The cache key is FNV-1a over the source, compiler path, flags and the contents of runtime.h. Libraries live in .wb_cache/ ($WB_CODEGEN_CACHE), the compiler is $WB_CXX (default clang++), and loaded libraries stay loaded for the life of the process.

runtime.h (ABI 4)

Compiled into every library and included by the host. No STL, only <cstdint> / <cstddef>, so a query compiles fast. It defines the ABI structs, GroupRows<Row> (rows inline in hash slots), MedianStore and JoinTable, each mirroring the vectorized engine's algorithm.

Produce / consume: one fused loop per pipeline

src/codegen/generator.cpp walks the plan top-down. produce() on a Scan opens a new pipeline function with a row loop; every operator above it consumes by appending code into that loop's body. A Filter adds if (!(…)) continue; per conjunct, an Aggregate adds the group lookup and per-row updates. A HashJoin is a pipeline breaker: its build side becomes its own pipeline that appends rows to a JoinTable (finalized once the pipeline finishes: stable sort, then one (key, first, count) bucket per key), and the probe side loops over each tuple's matches inline.

Specialized per FOR width signature

A segment's width signature packs the code width of each Int64 column the scan reads (2 bits each). Each pipeline's segment function is a template on its code types, instantiated once per signature present in the table, and a switch (seg.width_sig) dispatches every segment. A signature the library was not compiled for returns an error.

Lazy column loads

A column is decoded at its first use, in whatever scope the code is in then (HyPer's "load attributes when first touched"). After a filter, later columns are only read for surviving rows. The catch: a load placed after a branch cannot be hoisted above it, which matters for Q3 below.

Generated pipeline for Q4 (abridged)

struct Row { int64_t count; double s0; };

template <class C0>
void p0_seg(const wb_rt::SegmentRef& seg, State& st) {
    const C0* c0 = static_cast<const C0*>(seg.cols[0].data);      // device_id codes
    const uint64_t b0 = static_cast<uint64_t>(seg.cols[0].base);   // FOR base
    const double* f1 = static_cast<const double*>(seg.cols[1].data);
    for (uint32_t i = seg.lo; i < seg.hi; ++i) {
        const double v0 = static_cast<double>(f1[i]);
        const int64_t v1 = static_cast<int64_t>(b0 + static_cast<uint64_t>(c0[i]));
        {
            bool fresh = false;
            Row& e = *st.groups.find_or_insert(v1, fresh);
            if (fresh) e = Row{0, 0};
            ++e.count;
            e.s0 += v0;
        }
    }
}

int p0(const wb_rt::ScanInput& in, State& st) {
    for (uint32_t s = 0; s < in.num_segs; ++s) {
        const wb_rt::SegmentRef& seg = in.segs[s];
        switch (seg.width_sig) {
        case 1u: p0_seg<uint16_t>(seg, st); break;   // device_id in 2 B; one case per signature in the table
        default: return 1;
        }
    }
    return 0;
}

After the pipelines, wb_query walks st.groups in first-seen gid order and hands each group to the host as one row of 64-bit patterns through QueryOutput::emit_row. A global aggregate instead keeps one Row acc in a local per segment, continuing from st.acc, so its summation order is exactly the vectorized engine's.

Grouped aggregation: compiled ≈ 2×

With state inline in the slot, the fused per-row update touches one cache line per row. The vectorized engine's per-aggregate passes cannot exploit that layout. (Before inline state, Q4 was a tie.)

Joins: about even

The compiled engine's earlier 1.86× on Q5 was mostly the vectorized join's per-batch output materialization, not the execution model. With reused output columns the vectorized join is as fast or faster.

Selective filters: vectorized wins

Q2: clang if-converts the generated branch, so all 10M rows run a dependent fadd. Q3: lazy loading puts device_id's load after an unpredictable branch, so the loop cannot be if-converted. Branchless selection vectors win both.

One-off cost per cold query Generating takes under 0.1 ms, compiling 45–93 ms, and loading 155–230 ms: the first dlopen of a newly written .dylib costs more than compiling it, while re-opening a cached file in a later process takes 0.25–0.87 ms (codegen spec §11). For the filter queries Q2 and Q3 the compiled engine never repays that cost.
