Key property: columnar, not row-oriented All device_id values live together in one contiguous std::vector<int64_t>. All ts values in another. A query that only reads ts and value never touches device_id memory — even if it's in the same segment.

Primary Index (Sparse)

When a Table is sorted by a key column, each Segment gets a sparse index mapping granule start positions to their key values. Enables binary-search within a segment.

Without index

Scan starts at row 0 and applies the filter predicate to every row. With 65,536-row segments, that's 65,536 comparisons per segment even if only 100 rows match.

With sparse index (granule_size = 8192)

The index has 8 entries for a 65,536-row segment. Binary search finds the first granule that could satisfy ts > cutoff, and the scan starts there — skipping up to 57,000 rows without reading them.

v1 — Row-at-a-Time (Volcano Model)

The first version of ScanOperator returned one ScanRow per next() call — the classic Volcano iterator. Simple, but one virtual call per row.

ScanRow — the original return type

// operator.h (original)
struct ScanRow {
    std::size_t segment_idx;   // which segment
    std::size_t row_idx;       // which row within that segment
};

class Operator {
    virtual std::optional<ScanRow> next() = 0;
};

How the caller used it

// Counting rows — one virtual call per row
ScanOperator scan{t, std::nullopt};
std::size_t count = 0;
while (auto row = scan.next())  // returns ScanRow{seg=1, row=3}
    ++count;                          // just counting — never reads column data

The cost — 4 dispatches per row

Inside matches() — per row

  1. std::visit on predicate variant → type dispatch
  2. Generic lambda instantiation
  3. static_cast to typed vector
  4. switch(op) for comparison

All 4 steps are constant for the entire batch — the predicate never changes between rows. Yet we paid for them 10M times.

The per-row matches() call

// Called once per row — brutal
static bool matches(const Vector& col,
                     uint32_t row,
                     const Predicate& pred) {
    return std::visit(          // ← dispatch #1
        [&](const auto& pval) {
            if constexpr (...)       // ← dispatch #2
                auto v = cast(col)[row]; // ← dispatch #3
                switch(pred.op) ...      // ← dispatch #4
        }, pred.value);
}

Why the row model was kept at all ScanRow is conceptually clean for explaining execution — "give me the next row". The Volcano model is in every textbook. We built it first to prove the pipeline works, then replaced the return type with Batch to amortise call overhead. The operator interface (next(), nullopt = done) stayed identical.

v2 — Batch Model (Vectorized)

Zero-copy design The column data is never copied. The Batch holds three raw pointers borrowed from the Segment. set_sel() stores a vector<uint32_t> of row indices — that's the only allocation per batch after the filter runs. The Segment's data stays untouched.

AggHashTable — flat open-addressing vs std::unordered_map

std::unordered_map (old)

Each bucket is a linked list of heap-allocated nodes. A lookup for key K:
1. Hash K → bucket index
2. Load bucket pointer (cache miss #1)
3. Walk linked list (cache miss #2, #3…)

With 10K groups and 10M inserts: ~20M random heap pointer dereferences.

AggHashTable (flat)

One contiguous vector<Slot>. A lookup:
1. Knuth hash K → slot index
2. Linear probe until key matches or empty
3. All slots in the same array → sequential memory

Load factor 30% (32K slots, 10K groups) → near-zero probe chains. ~1.7× faster.
