wb — Columnar Engine Internals

A from-scratch columnar analytical database written in C++20.
Covers storage layout and encoding, execution model, pruning, vectorized filtering, aggregation, joins, and a compiled (codegen) engine that runs the same plans.

wb is a minimal but realistic columnar query engine. It ingests CSV data into immutable column-oriented segments, attaches min/max zone maps and a sparse primary index for pruning, and executes queries as a pipeline of pull-based operators that pass batches of row indices rather than materialising rows.

Queries are written as a small logical plan (Scan / Filter / HashJoin / Aggregate). The same plan runs on two engines: the vectorized operator pipeline (run_vectorized) and a HyPer-style compiled engine that generates C++, compiles it with clang and loads it with dlopen (run_compiled). The two must return bit-identical results.

Storage model

Columns grouped into immutable segments. Int64 columns are frame-of-reference encoded in 1/2/4/8-byte codes; Float64 columns store double (or float on opt-in). No row materialisation.

Execution model

Volcano/iterator model, but pull-at-a-batch (not pull-at-a-row). Each next() call returns up to 4,096 row slots.

Pruning

Zone maps (exact min/max per column per segment) let the scan skip entire segments before reading a single byte of column data.

Filtering

Branchless template kernels with std::greater<> et al. baked in at compile time. Dispatch on type × encoding × operator happens once per batch, not once per row.

Aggregation & joins

Hash aggregation (COUNT, SUM, MIN, MAX, AVG, exact MEDIAN) with group state inline in hash slots, and an inner equi-join on one int64 key.

Compiled engine

Produce/consume code generation into one fused loop per pipeline, specialised per encoding width, cached on disk by an FNV-1a key.

Type System

All column types flow from a single enum in schema.h:

enum class DataType : std::uint8_t {
    Int64,    // 8-byte signed integer
    Float64,  // 8-byte IEEE 754 double
    String,   // heap-allocated std::string
};

struct ColumnDef {
    std::string name;
    DataType    type;
    bool        narrow_float = false;  // Float64 only: store as float (lossy, opt-in)
};
using Schema = std::vector<ColumnDef>;

A Schema is just an ordered list of column definitions. Every object in the engine that is aware of column types receives a Schema — the builder, the loader, and any operator that needs to downcast a Vector*. narrow_float changes only the storage of a Float64 column; its logical type and every read stay double. It is exact only for inputs with at most 6 significant decimal digits.

The plan layer and the compiled engine accept only Int64 and Float64 columns (plan::output_types rejects String); String columns remain usable by ScanOperator and FilterOperator directly.

Why only three types? Three types is the minimum to demonstrate all dispatch patterns without drowning in boilerplate. Adding Int32, Boolean, or Timestamp is mechanical — every switch on DataType gets one new case.

Column Vectors

Each column type gets a concrete class. Columns are immutable once constructed: there is no append(). SegmentBuilder buffers raw values and builds the encoded column in seal().

/* Abstract base — no data, only type/size/footprint contract */ Vector { type() → DataType, size() → size_t, memory_bytes() → size_t } │ ├─ Int64Vector codes_: variant<vector<uint8_t|uint16_t|uint32_t|uint64_t>>, base_ │ visit(f) → f(span<const UInt> codes, int64_t base) ├─ Float64Vector values_: variant<vector<double>, vector<float>> │ visit(f) → f(span<const double>) or f(span<const float>) └─ StringVector values_: vector<string> data() → const vector<string>&

Int64: frame-of-reference encoding

Int64Vector stores value − base, where base is the column's minimum within the segment, in the narrowest unsigned width that holds the column's range: 1, 2, 4 or 8 bytes per value. Decoding is a widen-and-add, done as an unsigned add so a range that needs all 64 bits wraps instead of overflowing:

Segment range (max − min)Code typeBytes / value
≤ 255uint8_t1
≤ 65,535uint16_t2
≤ 4,294,967,295uint32_t4
anything largeruint64_t8
template <typename Code>
static int64_t decode(int64_t base, Code code) {
    return static_cast<int64_t>(static_cast<uint64_t>(base) + code);
}

Hot loops never decode through a virtual call or a per-row switch. They call visit(), which resolves the width once per batch and hands the kernel a typed code array, so the inner loop is specialised for one width:

static_cast<const Int64Vector&>(col).visit([&](auto codes, int64_t base) {
    for (uint32_t i : rows)
        sum += Int64Vector::decode(base, codes[i]);   // codes: span<const uint16_t>, say
});

value(i) gives scalar access for cold paths, and raw() returns an untyped {codes, base, width} view that the compiled engine binds into generated code.

Float64: double, or float on opt-in

Float64Vector stores double, or float when the column's ColumnDef::narrow_float is set. Reads always widen to double. Narrow storage halves the column but is lossy in general, so it is never chosen automatically.

Operator-owned output vectors

Two mutators exist, for operator-owned output columns only: Int64Vector::reset_plain(n) turns the vector into an unencoded column (width 8, base 0, so decoding is the identity) and Float64Vector::reset(n) into a double column. Both keep the existing capacity, so refilling a batch-sized output column allocates nothing. HashJoinOperator uses them; segment columns are never reset.

Downcast safety The static_cast to a concrete vector is safe only when the caller already checked col.type() (or the plan was validated, which fixes every column's type). The filter dispatch switches on col.type() first. An unchecked downcast to the wrong type is undefined behaviour.

Zone Maps

Every column in every segment carries one ZoneMap — the exact min and max value observed. Zone maps are updated during SegmentBuilder::append_* and frozen at seal() time. They never change after that. One exception at seal: for a narrow_float column, rounding to float can move a value past the double min/max, so seal() rebuilds that zone map from the stored values. Pruning then agrees with what the filter actually reads.

class ZoneMap {
    bool     has_values_ = false;
    DataType type_;
    std::variant<int64_t, double, std::string> min_, max_;
public:
    void observe(int64_t v);   // called for every appended value
    void observe(double v);
    void observe(const std::string& v);
};

At query time, zone_map_can_match(zm, op, value) returns false (prune this segment) only when the zone map proves no row can satisfy the predicate:

OpPrune whenIntuition
col == vv < zmin || v > zmaxv outside the segment's range
col != vzmin == zmax == vevery value is v; nothing differs
col < vzmin >= veven the smallest value isn't less
col <= vzmin > veven the smallest value exceeds v
col > vzmax <= veven the largest value isn't greater
col >= vzmax < veven the largest value falls short
Real-world result On 10M rows with a monotonically-increasing timestamp column split into 153 segments of 65,536 rows each, a ts > midpoint predicate prunes 75 of 153 segments — 49% of the table skipped before reading a single byte of column data.

Segments & SegmentBuilder

A Segment is immutable after creation. It owns its encoded column vectors (via std::unique_ptr), one zone map per column, and a sparse primary index. The builder constructs all of them at seal time and moves them in.

Segment │ num_rows_ = 65,536 │ ├─ columns_[0] → Int64Vector base=ts_min, codes [ts₀−base, ..., ts₆₅₅₃₅−base] ├─ columns_[1] → Float64Vector [v₀, v₁, ..., v₆₅₅₃₅] (double, or float if narrow) │ ├─ zones_[0] → ZoneMap Int64 min=1700000000 max=1700065536 ├─ zones_[1] → ZoneMap Float64 min=5.1 max=94.9 │ └─ primary_index_ → [{key@row 0, 0}, {key@row 8192, 8192}, ...] (only if the table has a sort key)

SegmentBuilder manages the mutable accumulation phase. It holds one raw buffer per column (vector<int64_t>, vector<double> or vector<string>) and does no encoding until seal():

SegmentBuilder b{schema};
b.append_int64(0, ts);         // col 0, col 1 must alternate to form rows
b.append_float64(1, value);   // num_rows_ increments on col 0 append
// ... 65,535 more rows ...
auto seg = b.seal(table.sort_key_col(), /*granule_size=*/8192);  // builder left empty

What seal() does

  1. Asserts every column buffer has num_rows_ values.
  2. If there is a sort key (it must be Int64): computes a permutation that sorts rows by the key, applies it to every column buffer in lockstep, and records one IndexEntry{sort_key_value, row_offset} per granule of granule_size rows. This is the sparse primary index.
  3. Encodes each buffer into its immutable column: frame-of-reference for Int64, double/float for Float64, moved strings for String.
  4. For narrow Float64 columns, rebuilds the zone map from the stored floats.

Sorting is per segment only. Segments are not merged or re-sorted against each other.

Row counting convention num_rows_ increments when col_idx == 0 is appended. This counts rows started, not rows completed — consistent if someone reads num_rows() mid-row. seal() asserts all columns have equal length.

String append — observe-before-move

In append_string, the zone map observes the value before std::move transfers ownership. After a move, the string is in a valid-but-unspecified state (usually empty). Observing an empty string would corrupt the zone map's min with "", which sorts before every non-empty string.

zones_[col_idx].observe(value);                          // ← observe FIRST
static_cast<StringVector*>(columns_[col_idx].get())->append(std::move(value)); // ← then move

Table

A Table is an ordered, append-only sequence of segments. It owns all segments via unique_ptr and never reorders or merges them.

class Table {
    std::optional<std::size_t>            sort_key_col_;  // Int64 column sorted within each segment
    std::string                           name_;
    Schema                                schema_;
    std::vector<std::unique_ptr<Segment>> segments_;
public:
    Table(std::string name, Schema schema, std::optional<std::size_t> sort_key_col = std::nullopt);
    void             add_segment(std::unique_ptr<Segment>);
    const Segment&  segment(size_t i) const;
    std::size_t      num_segments()    const;
    std::optional<std::size_t> sort_key_col() const;
};

Segments are logically ordered by insertion order. There is no global index — the scan operator iterates segment(0) .. segment(n-1) and relies on zone maps to skip irrelevant ones. Within a surviving segment, a table with a sort key also has the per-segment sparse primary index, which lets the scan start past rows that cannot match (see Scan Operator). The benchmark readings table is sorted on ts (column 1).

CSV Loader

load_csv(table, path, rows_per_segment = 65536) streams the file line by line, parsing each field and appending to a SegmentBuilder. Every rows_per_segment rows it calls seal(table.sort_key_col(), 8192) and starts a fresh builder.

Key properties:

  • Bounded staging — only one segment's raw buffers are held in the builder at a time
  • Header validation — CSV column names must match schema column names in order
  • Partial final segment — last segment sealed even if < rows_per_segment rows
  • Type dispatch via switch(DataType) per field
  • No quote handling — fields are split on every comma

No allocation per row

split_csv_line splits a line into a std::vector<std::string_view> that is cleared and reused for every row, so after the first row splitting allocates nothing. Int64 fields are parsed with std::from_chars; Float64 fields with std::strtod (not every libc++ the project builds against has the floating-point from_chars overload). Both reject trailing garbage. String fields are still copied into a std::string.

Performance note bench/results/baseline.txt vs after-footprint.txt (10M readings): load time 2,163 ms → 1,130 ms, allocations 30,010,877 (3.00/row) → 11,339 (0.00/row).

Batch

A Batch is a non-owning view over a window of rows. Both its column list and its selection vector are std::spans borrowed from buffers owned by the operator that produced it, so building a batch allocates nothing.

class Batch {
    std::span<const Vector* const> columns_;  // borrowed from the producer
    std::span<const uint32_t>       sel_;      // borrowed; meaningful only if has_sel_
    uint32_t                        offset_;   // first row in column arrays
    uint32_t                        size_;     // live row count in this batch
    bool                            has_sel_;  // false = rows [offset, offset+size) all live
public:
    void set_sel(std::span<const uint32_t> sel);  // borrows; sets size_ = sel.size()
};

A segment's columns come from ScanOperator::batch_cols_; an aggregate's or join's output columns from that operator's own vectors; the selection vector from FilterOperator::survivors_buf_.

Segment column (65,536 elements): [ ··· | ts₄₀₉₆ ts₄₀₉₇ ··· ts₈₁₉₁ | ··· ] ▲ ▲ offset=4096 offset+size=8192 Batch { offset=4096, size=4096, sel=absent } → rows 4096..8191 are all live After filter (only ~2000 pass ts > cutoff): Batch { offset=4096, size=2014, sel=[4097, 4103, 4105, ...] } ▲ absolute indices into the column array

Lifetime contract: a batch is valid only until the next call to next() on the operator that produced it (or any operator upstream of it), and only while the underlying segment is alive. Callers must not hold a batch across a subsequent next() call. That is what lets the producer reuse its column-pointer and selection buffers. Anything that must outlive the batch (a join's build side, an exchange payload) is copied into an owned Chunk.

Selection vector semantics

When has_sel() is false, the live rows are the contiguous range [offset, offset + size). When true, sel()[j] is an absolute index into the column arrays — each entry is a row that survived all filters applied so far. Stacking filters is just intersection: the second filter iterates sel rather than the full range.

for_each_live_row(batch, f) hides that split: it calls f(row) for every live row, with row an absolute index, whichever form the batch has.

Operator Model

Every operator inherits from Operator:

class Operator {
public:
    virtual ~Operator() = default;
    virtual std::optional<Batch> next() = 0;  // nullopt = exhausted
};

Operators today: ScanOperator, FilterOperator, HashAggOperator and HashJoinOperator. The aggregate and the join's build side are pipeline breakers: they drain a child completely on their first next().

This is the Volcano / iterator model, but lifted from row-at-a-time to batch-at-a-time. Each call to next() returns one Batch or std::nullopt when exhausted. The pipeline is lazy — no work happens until the caller drives the loop.

// Typical query driver loop: while (auto batch = filter.next()) { // pulls from filter // filter.next() internally calls scan.next() ← pulls from scan // scan.next() reads from the Table ← reads from storage const auto& vals = static_cast<const Float64Vector&>(batch->column(1)); for_each_live_row(*batch, [&](uint32_t i) { sum += vals.value(i); }); }

Scan Operator

The ScanOperator is the only operator that touches storage. It iterates segments in order, applies zone-map pruning, and emits batches of up to target_batch_size rows (default 4,096).

ScanOperator(
    const Table&              table,
    std::optional<Predicate>  predicate,      // used for zone-map pruning only
    uint32_t                  target_batch_size = 4096,
    std::vector<size_t>       projected_cols    = {}   // empty = all columns
);

State machine inside next()

while (true) {
    if (seg_idx_ >= table_.num_segments()) return nullopt;  // exhausted

    if (!seg_initialized_) {
        // Zone-map check: can this segment possibly match the predicate?
        if (predicate_ && !zone_map_can_match(...)) {
            ++segments_pruned_;  ++seg_idx_;  continue;  // skip entire segment
        }
        ++segments_scanned_;
        if (predicate_ is on table.sort_key_col())        // sparse primary index
            row_idx_ = scan_start_row(seg.primary_index(), *predicate_);
        batch_cols_ = projected column pointers;        // rebuilt once per segment
        seg_initialized_ = true;
    }

    remaining = seg.num_rows() - row_idx_;
    if (remaining == 0) { advance_to_next_segment(); continue; }

    batch_size = min(remaining, target_batch_size_);
    return Batch{batch_cols_, offset, batch_size};   // O(1): borrows batch_cols_
}

Sparse primary index: scan_start_row

When the predicate is on the table's sort key, scan_start_row(idx, pred) binary-searches the segment's IndexEntry list for the last granule whose first key is ≤ the literal and starts the scan there. It skips rows only for >, >= and ==; for <, <= and != it returns 0. It is a public free function in exec/scan.h because the compiled engine's host calls the same function, so both engines read identical row ranges. The scan does not stop early at the upper end; the filter removes the rest.

Projection projected_cols = {1, 2} means the batch contains only original columns 1 and 2 at batch positions 0 and 1. Downstream operators must use remapped indices. Saves no bandwidth unless the consumer actually reads the discarded columns' data — because column data is only fetched when dereferenced, not when the pointer is borrowed.

Filter Operator

The FilterOperator wraps any child operator and applies a single-column predicate per batch. The critical design is that all dispatch happens once per batch, not once per row.

std::optional<Batch> FilterOperator::next() {
    while (true) {
        auto batch = child_->next();
        if (!batch) return nullopt;

        const Vector& col = batch->column(predicate_.col_idx);

        // ONE type × encoding × op dispatch per batch:
        std::size_t n = 0;
        switch (col.type()) {
            case DataType::Int64: {
                int64_t lit = std::get<int64_t>(predicate_.value);
                static_cast<const Int64Vector&>(col).visit([&](auto codes, int64_t base) {
                    auto get = [&](uint32_t i) { return Int64Vector::decode(base, codes[i]); };
                    n = dispatch_op(*batch, get, predicate_.op, lit, survivors_buf_);
                });
                break;
            }
            // ...Float64 (visit: double or float storage), String mirrored
        }

        if (n == 0) continue;  // whole batch filtered out
        batch->set_sel({survivors_buf_.data(), n});  // borrowed, not copied
        return batch;
    }
}

Branchless kernel — the inner loop

template <typename Pred>
std::size_t select_rows(const Batch& batch, Pred pred, std::vector<uint32_t>& out) {
    if (out.size() < batch.size()) out.resize(batch.size());  // grows once, then reused
    uint32_t* dst = out.data();
    std::size_t n = 0;
    for (uint32_t i = batch.offset(); i < end; ++i) {  // or: for (i : batch.sel())
        dst[n] = i;        // always store the index...
        n += pred(i);     // ...advance the cursor only if it passed
    }
    return n;
}

dispatch_op switches on the CompareOp and calls select_rows with std::greater<> (etc.) baked in, so each instantiation sees one width, one comparison and one literal type at compile time. Every row index is written; only the cursor depends on the predicate, so there is no data-dependent branch and mid-selectivity filters do not pay for mispredictions. Downstream operators then touch only the survivors. In the codegen experiment this is where the vectorized engine won: Q2 value > 50 6.8 vs 13.7 ms, and Q3 (two predicates) 7.2 vs 35.3 ms, against generated code at -O3. Q3's generated loop kept a real, unpredictable branch; in Q2 clang if-converted the branch, so all 10M rows ran a dependent add (docs/superpowers/specs/2026-10-21-codegen-vs-vectorized-design.md §11).

Predicates

enum class CompareOp { Eq, Ne, Lt, Le, Gt, Ge };

struct Predicate {
    std::size_t                                col_idx;
    CompareOp                                  op;
    std::variant<int64_t, double, std::string> value;
};

A Predicate covers one column. Conjunctions live in the plan: plan::Filter holds a list of Compares, which run_vectorized lowers to one chained FilterOperator per conjunct, and translates the first conjunct to table numbering for the scan's pruning.

Hash Aggregation

HashAggOperator computes [GROUP BY group_col] with a list of aggregates. The group key must be Int64.

enum class AggKind : std::uint8_t { Count, Sum, Min, Max, Avg, Median };

struct AggSpec {
    AggKind     kind;
    std::size_t col  = 0;                // ignored for COUNT(*)
    DataType    type = DataType::Int64;
};

HashAggOperator(std::unique_ptr<Operator> child,
                std::optional<std::size_t> group_col,   // nullopt = global aggregate
                std::vector<AggSpec> aggs);

Output columns: the group key (Int64, if grouped), then one per aggregate. COUNT is Int64; SUM, MIN and MAX keep the input's type; AVG and MEDIAN are Float64. One row per group, in first-seen order. The first next() drains the child, builds the output columns and then emits them in batches of 4,096.

Group state inline in hash slots: GroupSlots

Each group's aggregate state is a fixed-size block stored inside its hash slot:

slot
key int64
gid uint32 + pad
state: __int128 sums · count · 8-byte fields · MedianHandles

Slots are 16-byte aligned. Open addressing with linear probing, a multiplicative hash (key × 0x9E3779B97F4A7C15, low bits), power-of-two capacity and load factor ≤ 0.5. Group ids are dense and first-seen (0, 1, 2, …) and give the output order. INT64_MIN is the empty-slot marker, so that one key's state lives outside the slot array.

Two passes per batch

  1. Pass 1 — reserve(size() + rows), so the table cannot rehash during the batch; then for each live row, find_or_insert its key, initialise a fresh group, increment its count and store the row's state pointer in ptrs_.
  2. Pass 2 — one loop per aggregate over ptrs_, updating state in place. The column's encoding is resolved once per loop via visit().

A global aggregate has a single state block. Each aggregate accumulates in a local variable for the batch (a register, not a memory read-modify-write per row), in row order.

Semantics (shared with the compiled engine)

AggregateRule
COUNT(*)Int64 count of live rows per group
SUMStarts at 0 / +0.0 and every row adds. SUM(Int64) accumulates in __int128 and throws std::overflow_error at output if the result does not fit in int64.
AVGSame accumulator as SUM, divided by the count as double
MIN / MAXStart at the group's first value, update with v < m || v != v (resp. >): a NaN wins and stays
MEDIANExact. Values collected per group in the column's storage type, selected under median_less: numbers ascending with -0.0 before +0.0, then NaNs ordered by bit pattern. Even counts average the two middle values.
Global aggregate over no rows HashAggOperator emits no row in that case. SQL wants one row, so run_vectorized (src/plan/lower_vec.cpp) appends it with QueryResult::append_empty_aggregate_row: COUNT columns 0, every other column NULL. The compiled engine's host does the same.

The older AggHashTable (key → {sum, count}) remains for parallel_group_sum_count, the multi-threaded GROUP BY SUM/COUNT path in which workers claim one segment at a time through an atomic counter.

MEDIAN Storage

Exact MEDIAN must keep every value. MedianStore<T> (T = int64_t, double, or float for narrow columns) keeps them in per-group chains of 2 KiB blocks, carved from 128 KiB chunks of 64 blocks that never move. There is no doubling and no copy on growth. A group's inline state holds only a MedianHandle{head, tail, count}.

chunks_[0] (128 KiB) [blk0][blk1][blk2] ... [blk63] chunks_[1] ... next_[b], size_[b] per-block headers kept out of band, so a block is exactly 2 KiB (256 int64/double or 512 float — a power of two) group 7: head ─► blk2 ─► blk9 ─► blk40 ◄─ tail count = 700

Finalize

  • Grouped: each chain is copied into one scratch vector reused across groups and selected with std::nth_element under median_less.
  • Global: the only chain's blocks are consecutive and all full but the last, so value i is at block head + i / 256 (or 512), slot i % 256. The median is selected in place by an introselect through that accessor: three-way quickselect with a median-of-3 pivot, falling back to heapsort after about 2·log₂ n rounds, so the worst case is O(n log n). No second copy of the values is made.
Effect Q7 (median by device, 10M rows) peak memory went from 382.9 MiB to 89.0 MiB on the vectorized engine; Q8 (global median) from 381.3 to 75.9 MiB; Q7 on a narrow_float column 51.2 MiB (docs/superpowers/specs/2026-10-21-footprint-fixes-design.md §7).

Hash Join

HashJoinOperator(probe, build, probe_key_col, build_key_col) is an inner equi-join on one Int64 key. Output columns are every probe column, then every build column. Duplicate keys on either side give the full cross product per key, and probe batches may carry a selection vector.

Build side

  1. On the first next(), drain the build child and copy every live row into one owned Chunk (batches die at the next next()).
  2. Stable-sort the rows by key into a second chunk, so all rows of a key are contiguous.
  3. Index each run of equal keys as a Bucket{key, first, count} (16 B per distinct key): open addressing, linear probing, load factor ≤ 0.5, indexed by the top bits of the multiplicative hash.

Probe side

Each probe batch's live rows and decoded keys are collected once; matches are gathered into output batches of at most 4,096 rows. An output batch never spans two probe batches, because pulling the next probe batch invalidates the current one.

For Int64/Float64 joins the output columns are owned by the operator and refilled in place by every next(), using reset_plain / reset, so there is no per-batch allocation. A join with any String column falls back to sealing fresh chunks per output batch.

Effect Reusing output columns cut Q5 (join + group by region) on the vectorized engine from 21.8 to 11.5 ms, and allocations per run from about 31,000 to 301 (docs/superpowers/specs/2026-10-21-footprint-fixes-design.md §7).

Plan IR

src/plan/plan.h defines a small logical plan shared by both engines. Column references are positions in the child's output, as with the operators.

struct Scan      { const Table* table; std::vector<size_t> cols; };
struct Filter    { NodePtr child; std::vector<Compare> conjuncts; };   // AND
struct HashJoin  { NodePtr probe, build; size_t probe_key, build_key; };
struct Aggregate { NodePtr child; std::optional<size_t> group_col; std::vector<AggExpr> aggs; };

struct Node { std::variant<Scan, Filter, HashJoin, Aggregate> op; };

validate_query checks the plan: Int64/Float64 columns only, column references in range, literal types matching their columns, Int64 join and group keys, and exactly one Aggregate, at the root. Every query is therefore an aggregate, and its answer is a QueryResult: typed columns with a validity byte per row, sorted by group key by canonicalize() so emission order does not matter.

Compiled Engine

The compiled engine is a HyPer-style data-centric code generator. Instead of passing batches between operators, it fuses each pipeline into one tight loop over a segment's rows.

plan ──bind_scans()──► ScanBindings (projected Int64 cols, width signatures, prune predicate) │ ▼ generate() produce/consume C++ source ── FNV-1a cache key (source + compiler + flags + runtime.h) ──┐ │ │ ▼ in-memory cache ─► on-disk cache (.wb_cache/<key>.dylib) ─► $WB_CXX (clang++) dlopen(RTLD_NOW) ─► dlsym wb_query + ABI check │ ▼ execute(): prune segments exactly like ScanOperator, bind columns into QueryInput wb_query(input, output) ─► emit_row() ─► QueryResult

Produce / consume

generate() walks the plan: produce(node, consume) on a Scan opens a per-segment row loop and calls the parent's consume with lazily loaded columns (a column is decoded at first use, HyPer's "load attributes when first touched"). A Filter's consume emits an if; a HashJoin produces its build side first, filling a join table, then its probe side, looping over each probe tuple's matches; the Aggregate's consume updates a group record. Scans are numbered in pre-order, build side before probe side, which is also the order pipelines run.

Specialised per FOR width signature

A segment's width signature packs the code width of the scan's k-th Int64 column into bits 2k..2k+1. bind_scans collects the distinct signatures across the table's segments; the generator emits one instantiation of the pipeline per signature and a switch (seg.width_sig) that dispatches each segment. A library asked to run a signature it was not compiled for reports an error.

runtime.h (ABI 4)

src/codegen/runtime.h is compiled into every generated library and included by the host, so both share one definition of the ABI structs (ColumnRef, SegmentRef, QueryInput, QueryOutput). It includes only <cstdint>/<cstddef>, no STL, and allocates with __builtin_malloc, so generated code compiles quickly and never depends on engine struct layouts. kAbiVersion = 4; the host rejects a library built against another version. Its data structures mirror the vectorized engine's algorithms, so benchmarks compare execution models rather than hash tables:

GroupRows<Row>GroupSlots: same hash, probing, initial capacity and growth; Row defined by the generated code, stored inline
MedianStore<T>exec/median_store.h: 2 KiB blocks, 64-block chunks, same introselect

Compile and cache

Flags: -std=c++20 -O<n> -march=native -fPIC -shared plus $WB_CODEGEN_EXTRA_FLAGS. The cache key is FNV-1a 64 over the source, compiler path, flags and the contents of runtime.h. Libraries stay loaded for the life of the process. Every failure throws CodegenError; the engine never silently falls back to the vectorized path.

One-off cost Per cold query: generate under 0.1 ms, compile 45–93 ms, load 155–230 ms. The first dlopen of a newly written .dylib costs more than compiling it; reopening a cached file in a later process takes 0.25–0.87 ms (docs/superpowers/specs/2026-10-21-codegen-vs-vectorized-design.md §11).

Engine Parity

Both engines must return bit-identical results: QueryResult::operator== compares doubles by bit pattern and treats NULL as equal to NULL. That requirement shapes the implementation:

  • Pruning is identical: the host calls the same zone_map_can_match and scan_start_row on the same first conjunct.
  • Float sums are added in the same row order in both engines (the compiled global aggregate continues from the previous segment's accumulator), so no reassociation and no SIMD reductions.
  • MIN/MAX NaN rules, __int128 SUM overflow and median_less are specified once and implemented in both.
  • A global aggregate over no rows gets the same COUNT-0 / NULL row from both hosts.

wb_codegen checks every query on the vectorized engine and on generated code at -O1 and -O3; tests/test_codegen.cpp covers the same ground in the test suite.

Distributed Layer

src/dist/ simulates a Redshift cluster in one process: nodes × slices, each slice holding its own part of every table and run on its own thread.

  • DISTSTYLE — EVEN (round-robin), KEY (slice_for_key, the high 32 bits of the multiplicative hash), ALL (one copy per node).
  • Exchange — redistribute on a key or broadcast, moving owned Chunks; NetworkStats counts bytes moved between slices.
  • Streams — run_stream runs one thread per slice; each exchange boundary is a barrier.
  • Join planner — the DS_* strategies (DS_DIST_NONE, DS_DIST_ALL_NONE, DS_DIST_INNER, DS_DIST_OUTER, DS_BCAST_INNER, DS_DIST_BOTH); among valid ones it picks the one that sends the fewest rows across nodes.

wb_dist runs the strategy, skew and crossover experiments.

Zone-Map Pruning

Zone maps are the single highest-leverage optimisation in the engine. They trade a few bytes of metadata per segment for the ability to skip entire segments with a scalar comparison at query planning time.

The function zone_map_can_match returns false (skip) only when the interval [zmin, zmax] has no overlap with the predicate's satisfying set. It is the dual of the filter: it proves absence rather than selecting presence. A false negative (saying "might match" when actually no row does) is safe — you scan extra rows. A false positive (saying "no match" when a row does match) would silently drop data.

75 segments pruned (49%) before any column data is read.
78 segments scanned (≈5.1M rows) — filter applied only to these.

Vectorized Filter Kernels

The key shift from naïve to fast: moving all dispatch above the inner loop.

Naïve — per row

std::visit on variant (type dispatch)
Generic lambda instantiation
static_cast to typed vector
switch(op) for comparison
× N rows per batch

Vectorized — per batch

switch(col.type()) once
visit() → code width (or float/double) once
dispatch_op → switch(op) once
run(std::greater<>{}) baked in at compile time
Inner loop: dst[n] = i; n += cmp(decode(base, codes[i]), lit)
No data-dependent branch in the loop

The auto run = [&](auto cmp) generic lambda is the mechanism. Each call site (run(std::greater<>{}), run(std::less<>{}), etc.) generates a distinct specialisation with a different Compare type, so no runtime polymorphism reaches the inner loop body. The same "resolve encoding once, then loop" pattern is used by HashAggOperator (for_each_int / for_each_double) and by the join's key decode and output gather.

Column Projection

ScanOperator accepts a projected_cols list. When non-empty, the batch's column array contains only those original columns, remapped to batch positions 0, 1, 2, …

When projection actually saves bandwidth In an in-memory engine with lazy evaluation, projection only reduces data movement if downstream code actually reads the discarded columns. Borrowing a pointer is free; only dereferencing the span data incurs cache lines. For disk-based or compressed storage, projection prevents decompressing irrelevant columns entirely — much larger win.

Buffer Reuse

The steady-state query path allocates nothing per batch. Every buffer a batch points at is owned by an operator and reused:

BufferOwnerReuse
survivors_buf_FilterOperatorGrown to the batch size once (resize, never shrunk); the emitted batch's selection span borrows it — no copy
batch_cols_ScanOperatorColumn pointers rebuilt once per segment; every batch's column span borrows it
ptrs_HashAggOperatorPer-batch state pointers, resized in place
out_vecs_HashJoinOperatorInt64/Float64 output columns refilled with reset_plain / reset, keeping capacity
fieldsload_csvOne vector<string_view> for every row's split

Because batches are spans into these buffers, the price is the lifetime contract: a batch dies at the producer's next next().

Effect ts > mid sum(value) on 10M rows: 2,472 allocations and 12.9 ms per query in bench/results/baseline.txt, 7 allocations and 4.9 ms in after-footprint.txt. These runs also include the column encoding changes, so the gain is not from buffer reuse alone.

Bottleneck analysis Filters favour the vectorized engine (branchless selection on unsorted data). Grouped aggregation favours the compiled engine: its fused per-row update touches one inline slot, while the vectorized engine makes one pass per aggregate. Joins are now a tie, since the earlier 1.7× compiled win on Q5 was mostly the vectorized join's per-batch materialisation. A cold compiled query still pays about 200–320 ms of compile + load, so it repays only on repeated runs.

What's Next

Fused vectorized SUM/COUNT

Vectorized Q4 missed its target (28.8 ms): pass 1 alone takes 21.2 ms. A fused path for SUM/COUNT-only aggregate lists could recover the old 18.9 ms loop.

Eager loads in generated code

Emit branch-free predicate evaluation for Q2/Q3, where lazy loading keeps an unpredictable branch in the generated loop.

Cheaper library load

The first dlopen of a new library (155–230 ms) costs more than compiling it. Code-signing or pre-warming generated libraries may cut load_ms.

Projection operator

Explicit ProjectOperator that materialises only the columns referenced downstream. Enables proper column-elimination before storage access for I/O-bound workloads.

Single-pass conjunctions

A plan Filter's conjuncts are lowered to chained FilterOperators today. A ConjunctivePredicate that applies all conditions in one kernel pass would avoid a selection-vector pass per conjunct.

Cross-segment clustering

Rows are sorted by the sort key within each segment at seal. Sorting across segments would make zone maps non-overlapping, so the scan could binary-search segments instead of checking each one.

Dictionary encoding

Replace StringVector with DictVector — store unique strings once, encode each row as a 16-bit integer. Cuts bandwidth and makes string comparison cheap.

Parquet / binary format

mmap a pre-columnarised binary file rather than parsing CSV. Eliminates the ~1.1 s parse of 10M rows; enables OS-level page cache for repeated queries.
