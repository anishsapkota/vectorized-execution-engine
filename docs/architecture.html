wb — Columnar Engine Internals

A from-scratch columnar analytical database written in C++20.
Covers storage layout, execution model, pruning, and vectorized filtering.

wb is a minimal but realistic columnar query engine. It ingests CSV data into immutable column-oriented segments, attaches min/max zone maps for pruning, and executes queries as a pipeline of pull-based operators that pass batches of row indices rather than materialising rows.

Storage model

Column-per-file layout within segments. Each column is a typed contiguous array (std::vector<T>). No row materialisation.

Execution model

Volcano/iterator model, but pull-at-a-batch (not pull-at-a-row). Each next() call returns up to 4,096 row slots.

Pruning

Zone maps (exact min/max per column per segment) let the scan skip entire segments before reading a single byte of column data.

Filtering

Template kernels with std::greater<> et al. baked in at compile time. Dispatch happens once per batch, not once per row.

Type System

All column types flow from a single enum in schema.h:

enum class DataType : std::uint8_t {
    Int64,    // 8-byte signed integer
    Float64,  // 8-byte IEEE 754 double
    String,   // heap-allocated std::string
};

struct ColumnDef { std::string name; DataType type; };
using Schema = std::vector<ColumnDef>;

A Schema is just an ordered list of column definitions. Every object in the engine that is aware of column types receives a Schema — the builder, the loader, and any operator that needs to downcast a Vector*.

Why only three types? Three types is the minimum to demonstrate all dispatch patterns without drowning in boilerplate. Adding Int32, Boolean, or Timestamp is mechanical — every switch on DataType gets one new case.

Column Vectors

Each column type gets a concrete class that owns a std::vector<T> and exposes a std::span<const T> for zero-copy read access:

/* Abstract base — no data, only type/size contract */ Vector { type() → DataType, size() → size_t } │ ├─ Int64Vector values_: vector<int64_t> append(int64_t) data() → span<const int64_t> ├─ Float64Vector values_: vector<double> append(double) data() → span<const double> └─ StringVector values_: vector<string> append(string) data() → span<const string>

Operators receive a const Vector& via the Batch API. When a kernel needs raw data it downcasts:

auto data = static_cast<const Int64Vector&>(col).data(); // span<const int64_t>
int64_t val = data[row_index];  // O(1), no bounds check in release
Downcast safety The cast is safe only when the caller already checked col.type() == DataType::Int64. Both the filter kernel dispatch and the benchmark sum loop do this check first. An unchecked downcast to the wrong type is undefined behaviour.

Zone Maps

Every column in every segment carries one ZoneMap — the exact min and max value observed. Zone maps are updated during SegmentBuilder::append_* and frozen at seal() time. They never change after that.

class ZoneMap {
    bool     has_values_ = false;
    DataType type_;
    std::variant<int64_t, double, std::string> min_, max_;
public:
    void observe(int64_t v);   // called for every appended value
    void observe(double v);
    void observe(const std::string& v);
};

At query time, zone_map_can_match(zm, op, value) returns false (prune this segment) only when the zone map proves no row can satisfy the predicate:

OpPrune whenIntuition
col == vv < zmin || v > zmaxv outside the segment's range
col != vzmin == zmax == vevery value is v; nothing differs
col < vzmin >= veven the smallest value isn't less
col <= vzmin > veven the smallest value exceeds v
col > vzmax <= veven the largest value isn't greater
col >= vzmax < veven the largest value falls short
Real-world result On 10M rows with a monotonically-increasing timestamp column split into 153 segments of 65,536 rows each, a ts > midpoint predicate prunes 75 of 153 segments — 49% of the table skipped before reading a single byte of column data.

Segments & SegmentBuilder

A Segment is immutable after creation. It owns its column vectors and zone maps via std::unique_ptr and moves them in from the builder at seal time.

Segment │ num_rows_ = 65,536 │ ├─ columns_[0] → Int64Vector [ts₀, ts₁, ..., ts₆₅₅₃₅] ├─ columns_[1] → Float64Vector [v₀, v₁, ..., v₆₅₅₃₅] │ ├─ zones_[0] → ZoneMap Int64 min=1700000000 max=1700065536 └─ zones_[1] → ZoneMap Float64 min=5.1 max=94.9

SegmentBuilder manages the mutable accumulation phase:

SegmentBuilder b{schema};
b.append_int64(0, ts);         // col 0, col 1 must alternate to form rows
b.append_float64(1, value);   // num_rows_ increments on col 0 append
// ... 65,535 more rows ...
auto seg = b.seal();            // unique_ptr<Segment>; builder is exhausted
Row counting convention num_rows_ increments when col_idx == 0 is appended. This counts rows started, not rows completed — consistent if someone reads num_rows() mid-row. seal() asserts all columns have equal length.

String append — observe-before-move

In append_string, the zone map observes the value before std::move transfers ownership. After a move, the string is in a valid-but-unspecified state (usually empty). Observing an empty string would corrupt the zone map's min with "", which sorts before every non-empty string.

zones_[col_idx].observe(value);                          // ← observe FIRST
static_cast<StringVector*>(columns_[col_idx].get())->append(std::move(value)); // ← then move

Table

A Table is an ordered, append-only sequence of segments. It owns all segments via unique_ptr and never reorders or merges them.

class Table {
    std::string                           name_;
    Schema                                schema_;
    std::vector<std::unique_ptr<Segment>> segments_;
public:
    void             add_segment(std::unique_ptr<Segment>);
    const Segment&  segment(size_t i) const;
    std::size_t      num_segments()    const;
};

Segments are logically ordered by insertion order. There is no global index — the scan operator iterates segment(0) .. segment(n-1) and relies on zone maps to skip irrelevant ones.

CSV Loader

load_csv(table, path, rows_per_segment) streams the file row by row, parsing each field and appending to a SegmentBuilder. Every rows_per_segment rows it calls seal() and starts a fresh builder.

Key properties:

  • O(1) memory — only one segment worth of data in RAM at a time during load
  • Header validation — CSV column names must match schema column names in order
  • Partial final segment — last segment sealed even if < rows_per_segment rows
  • Type dispatch via switch(DataType) per field
Performance note Loading 10M rows takes ~3 seconds. The bottleneck is std::stoll / std::stod string parsing plus std::getline line scanning — not segment building or zone-map updates. A custom SIMD integer parser (e.g. parse 8 digits in parallel) would cut this by 5–10×.

Batch

A Batch is a non-owning view over a window of rows within a segment. It holds borrowed pointers to column vectors, an offset into those arrays, and an optional selection vector identifying which rows are live.

class Batch {
    std::vector<const Vector*>                vectors_;  // borrowed, not owned
    std::optional<std::vector<uint32_t>>      sel_;      // absent = all rows live
    uint32_t                                  offset_;   // first row in column arrays
    uint32_t                                  size_;     // row count in this batch
};
Segment column (65,536 elements): [ ··· | ts₄₀₉₆ ts₄₀₉₇ ··· ts₈₁₉₁ | ··· ] ▲ ▲ offset=4096 offset+size=8192 Batch { offset=4096, size=4096, sel=absent } → rows 4096..8191 are all live After filter (only ~2000 pass ts > cutoff): Batch { offset=4096, size=2014, sel=[4097, 4103, 4105, ...] } ▲ absolute indices into the column array

Lifetime contract: a batch is valid only until the next call to next() on any operator in the pipeline. Callers must not hold a batch across a subsequent next() call. This allows column pointers to stay borrowed without copying data.

Selection vector semantics

When sel() is absent, the live rows are the contiguous range [offset, offset + size). When present, sel()[j] is an absolute index into the column arrays — each entry is a row that survived all filters applied so far. Stacking filters is just intersection: the second filter iterates sel rather than the full range.

Operator Model

Every operator inherits from Operator:

class Operator {
public:
    virtual std::optional<Batch> next() = 0;
};

This is the Volcano / iterator model, but lifted from row-at-a-time to batch-at-a-time. Each call to next() returns one Batch or std::nullopt when exhausted. The pipeline is lazy — no work happens until the caller drives the loop.

// Typical query driver loop: while (auto batch = filter.next()) { // pulls from filter // filter.next() internally calls scan.next() ← pulls from scan // scan.next() reads from the Table ← reads from storage for (uint32_t i : *batch->sel()) sum += vals[i]; }

Scan Operator

The ScanOperator is the only operator that touches storage. It iterates segments in order, applies zone-map pruning, and emits batches of up to target_batch_size rows (default 4,096).

ScanOperator(
    const Table&              table,
    std::optional<Predicate>  predicate,      // used for zone-map pruning only
    uint32_t                  target_batch_size = 4096,
    std::vector<size_t>       projected_cols    = {}   // empty = all columns
);

State machine inside next()

while (true) {
    if (seg_idx_ >= table_.num_segments()) return nullopt;  // exhausted

    if (!seg_initialized_) {
        // Zone-map check: can this segment possibly match the predicate?
        if (predicate_ && !zone_map_can_match(...)) {
            ++segments_pruned_;  ++seg_idx_;  continue;  // skip entire segment
        }
        ++segments_scanned_;
        seg_initialized_ = true;
    }

    remaining = seg.num_rows() - row_idx_;
    if (remaining == 0) { advance_to_next_segment(); continue; }

    batch_size = min(remaining, target_batch_size_);
    // Borrow projected column pointers
    return Batch{vecs, offset, batch_size};   // O(ncols) work
}
Projection projected_cols = {1, 2} means the batch contains only original columns 1 and 2 at batch positions 0 and 1. Downstream operators must use remapped indices. Saves no bandwidth unless the consumer actually reads the discarded columns' data — because column data is only fetched when dereferenced, not when the pointer is borrowed.

Filter Operator

The FilterOperator wraps any child operator and applies a single-column predicate per batch. The critical design is that all dispatch happens once per batch, not once per row.

std::optional<Batch> FilterOperator::next() {
    while (true) {
        auto batch = child_->next();
        if (!batch) return nullopt;

        const Vector& col = batch->column(predicate_.col_idx);

        // ONE type dispatch + ONE op dispatch per batch:
        switch (col.type()) {
            case DataType::Int64: {
                auto data = static_cast<const Int64Vector&>(col).data();
                int64_t lit = std::get<int64_t>(predicate_.value);
                dispatch_op(data, *batch, predicate_.op, lit, survivors_buf_);
            }
            // ...Float64, String mirrored
        }

        if (survivors_buf_.empty()) continue;  // whole batch filtered out
        batch->set_sel(survivors_buf_);
        return batch;
    }
}

Template kernel — the inner loop

template <typename T, typename Compare>
void filter_kernel_range(span<const T> data, uint32_t start, uint32_t end,
                          const T& lit, Compare cmp, vector<uint32_t>& out) {
    out.clear();
    out.reserve(end - start);
    for (uint32_t i = start; i < end; ++i)
        if (cmp(data[i], lit)) out.push_back(i);
}

When instantiated as filter_kernel_range<int64_t, std::greater<>>, the compiler sees one comparison per iteration with both operand types and the operator known at compile time. At -O3 -march=native this loop is eligible for NEON/AVX2 autovectorisation.

Predicates

enum class CompareOp { Eq, Ne, Lt, Le, Gt, Ge };

struct Predicate {
    std::size_t                                col_idx;
    CompareOp                                  op;
    std::variant<int64_t, double, std::string> value;
};

Zone-Map Pruning

Zone maps are the single highest-leverage optimisation in the engine. They trade a few bytes of metadata per segment for the ability to skip entire segments with a scalar comparison at query planning time.

The function zone_map_can_match returns false (skip) only when the interval [zmin, zmax] has no overlap with the predicate's satisfying set. It is the dual of the filter: it proves absence rather than selecting presence. A false negative (saying "might match" when actually no row does) is safe — you scan extra rows. A false positive (saying "no match" when a row does match) would silently drop data.

10M readings benchmark

153 segments × 65,536 rows. Predicate: ts > 1,705,000,000 (≈midpoint).
75 segments pruned (49%) before any column data is read.
78 segments scanned (≈5.1M rows) — filter applied only to these.

Vectorized Filter Kernels

The key shift from naïve to fast: moving all dispatch above the inner loop.

Naïve — per row

std::visit on variant (type dispatch)
Generic lambda instantiation
static_cast to typed vector
switch(op) for comparison
× N rows per batch

Vectorized — per batch

switch(col.type()) once
dispatch_op<T> → switch(op) once
run(std::greater<>{}) baked in at compile time
Inner loop: cmp(data[i], lit) only
Compiler can autovectorise the loop

The auto run = [&](auto cmp) generic lambda is the mechanism. Each call site (run(std::greater<>{}), run(std::less<>{}), etc.) generates a distinct specialisation with a different Compare type, so no runtime polymorphism reaches the inner loop body.

Column Projection

ScanOperator accepts a projected_cols list. When non-empty, the batch's column array contains only those original columns, remapped to batch positions 0, 1, 2, …

When projection actually saves bandwidth In an in-memory engine with lazy evaluation, projection only reduces data movement if downstream code actually reads the discarded columns. Borrowing a pointer is free; only dereferencing the span data incurs cache lines. For disk-based or compressed storage, projection prevents decompressing irrelevant columns entirely — much larger win.

Buffer Reuse

FilterOperator owns a persistent std::vector<uint32_t> survivors_buf_. The kernel fills it in-place via an out& parameter — out.clear() resets size but preserves allocation. After warmup (a few batches), the buffer's capacity stabilises at the high-water mark of survivors per batch and no further heap allocations occur for the building phase.

set_sel(survivors_buf_) copies the survivors into the Batch (the Batch owns its sel vector independently). The copy costs ~survivors × 4 bytes per batch but allows survivors_buf_ to retain capacity.

Design Decisions

DecisionChosenAlternative consideredReason
Segment mutability Immutable after seal Mutable, in-place update Simplifies ownership (unique_ptr, no locks), enables safe concurrent reads, matches real columnar engines (Parquet, ClickHouse)
Column storage std::vector<T> Flat byte buffer + manual offsets std::vector gives correct resizing semantics during build; span gives zero-copy access after seal
Execution granularity Batch (4,096 rows) Row-at-a-time (Volcano) or full-segment Amortises virtual call + function call overhead; fits L1 cache; enables SIMD in kernels; segments can be larger than cache
Selection vector vector<uint32_t> of row indices Bitmask; boolean column Index vector is faster when selectivity <50% (avoid iterating zeros); composable across filter stages; easy to sum over
Zone map type Exact min/max Bloom filter; histogram Exact min/max is lossless for range predicates, costs only 2 values per column per segment, zero false negatives
Builder lifecycle Single-use (exhausted after seal) Reusable (reset on seal) Eliminates "append after seal" bugs; simpler state machine; caller just constructs a new builder
num_rows_ counter Increment on col 0 append Increment on last-column append "Rows started" semantics — counter is never behind mid-row; seal() asserts column lengths equal as correctness check
Kernel dispatch Template + generic lambda (compile-time) std::function; virtual call; std::visit per row All dispatch resolves at compile time; inner loop is one instruction; compiler can SIMD-vectorise

Benchmarks

Query: SELECT sum(value) FROM readings WHERE ts > 1,705,000,000
Dataset: 10M rows, 3 columns (device_id int64, ts int64, value float64), 153 segments of 65,536 rows.
Machine: Apple Silicon (ARM), compiled with -O3 -march=native.

The dominant cost is CSV parsing, not query execution. The query itself (pruning + filter + sum over ~5M rows) runs in ~7.5 ms, of which most is DRAM bandwidth — reading ~41 MB of ts column data at ~50 GB/s gives a ~0.8 ms floor.

Bottleneck analysis We are memory-bandwidth bound on the filter, not compute-bound. The zone-map prune saves ~49% of segment reads. Within surviving segments the filter kernel runs at close to memory-line throughput. Further gains require either reducing data volume (smaller types, dictionary encoding) or reducing the number of rows that reach the filter (tighter zone maps via sorted ingestion order).

What's Next

Hash aggregation

GROUP BY device_id — hash table keyed on the group column, accumulate sum/count per bucket. First operator that produces more rows than it consumes (bucket enumeration phase).

Projection operator

Explicit ProjectOperator that materialises only the columns referenced downstream. Enables proper column-elimination before storage access for I/O-bound workloads.

AND-of-predicates

Chain two FilterOperators, or add a ConjunctivePredicate that applies multiple conditions in one kernel pass (avoids two selection-vector passes over the same data).

Sorted ingestion / clustering

Sort rows by the most-frequently-queried column before sealing. Zone maps become non-overlapping across segments — binary-search-style pruning instead of linear scan.

Dictionary encoding

Replace StringVector with DictVector — store unique strings once, encode each row as a 16-bit integer. Cuts bandwidth and makes string comparison cheap.

Parquet / binary format

mmap a pre-columnarised binary file rather than parsing CSV. Eliminates the 3-second parse time; enables OS-level page cache for repeated queries.
